# SIGHUP 中断后的运行元数据恢复设计

## 背景与事实

病例 `case_2` 的正式重采样在根清单完成 88,280 条时收到 `SIGHUP`，退出码为 129。四类状态清单计数之和与根清单完全一致，cgroup 的 `oom` 和 `oom_kill` 均为 0，日志中没有 Python traceback。

当前实现只在渲染阶段的 `finally` 中写 `run_metadata.json`。程序没有注册 `SIGHUP` 处理器，进程按该信号的默认动作直接终止时，`finally` 没有执行；而恢复入口要求已有姿态必须同时存在 `run_metadata.json`，因此完整的切面结果无法按既有协议继续。

## 目标与边界

目标是在不重算已完成切面、不降低恢复协议校验强度的前提下恢复本次任务，并避免后续 SSH 断开造成相同问题。

本修复只涉及运行状态和恢复元数据。它不得改变下列医学影像与采样行为：

- 400 个采样点及采样点间最小 10 mm 间距；
- roll `-15..15/5`、pitch `-10..10/5` 和既有三类 yaw 策略；
- RAS 坐标系、Origin/Direction、方形尺寸、输出分辨率和三次插值；
- CT FOV、黑区、直线黑边、血管求交、动静脉颜色和图库分类规则；
- 目标总切面数 208,250。

## 方案比较

### 方案 A：可审计元数据重建和启动期检查点（采用）

从当前配置、输入文件、核心设计哈希、Git commit 和重新生成的完整姿态计划计算恢复协议。严格验证已有根清单、四类状态清单、姿态 ID 和几何字段后，写入明确标记为中断恢复的元数据。正常运行在首个待处理切面前写入 `running` 检查点，结束时再写最终状态。

优点是保留 88,280 条有效结果、恢复校验不降级，并修复后续同类中断。代价是需要一个受控的元数据重建入口和针对生命周期的测试。

### 方案 B：保留部分结果并使用新输出目录全量重跑

协议最简单，但浪费已经完成的结果和约数小时计算，且服务器剩余磁盘同时保存部分结果和完整新结果的安全余量不足。不采用。

### 方案 C：手工写入最小 `resume_protocol_sha256` 或绕过缺失检查

实现最快，但不能证明已有清单与当前姿态计划、输入文件和构建一致，会削弱审计证据。不采用。

## 设计

### 1. 运行元数据生命周期

`run_metadata.json` 继续使用原子替换写入，并新增 `run_state`：

- `running`：运行协议和后端信息已经确定，渲染可能尚未开始或仍在进行；
- `interrupted`：捕获到普通 Python 异常或未完成退出，清单可用于恢复；
- `complete`：四类状态总数等于完整姿态数，后续索引和总结可以使用。

新任务必须在首个待处理切面写入前持久化 `running` 元数据。即使进程被直接终止而跳过 `finally`，磁盘上仍保留足以校验恢复的协议。

已有旧版完整元数据没有 `run_state` 时保持兼容，仍以 `resume_protocol_sha256` 为恢复门禁。

### 2. 中断元数据重建

新增显式恢复入口，只允许在以下条件全部成立时写入缺失的 `run_metadata.json`：

1. 元数据当前不存在，避免覆盖既有证据；
2. 调用者给出的预期完成数与根清单条数一致；
3. 根清单和四类状态清单可完整解析，状态唯一且摘要一致；
4. 当前配置重新生成的完整姿态 ID 集合无重复；
5. 每个已完成 ID 都属于当前姿态计划，四顶点和位姿字段通过既有严格比较；
6. 当前输入文件可重新计算 SHA-256，核心设计哈希和 Git commit 可确定；
7. 已有姿态中没有当前计划之外的陈旧 ID。

写入内容使用当前代码的 `_run_protocol_metadata` 结果，并包含：

- `run_state: interrupted`；
- `completed_pose_count` 和四类 `status_counts`；
- `total_squares`；
- `recovery_history`，记录原因 `sighup`、原退出码 129、恢复前清单计数和 UTC 时间；
- `compatible_completed_build_git_commits`，只列出重建时已完成记录中实际存在且格式有效的提交；恢复历史同时记录恢复实现的真实 Git commit；
- 完整 `resume_protocol_sha256` 和构成该摘要的协议字段。

该入口不加载 CT 体数据、不初始化 CPU/GPU 插值后端、不生成或改写任何 PNG/PLY/JSONL。

### 3. 恢复运行

恢复时仍由现有 `GalleryWriter` 读取并验证全部清单。`run_case` 比较重建元数据中的协议摘要与当前协议；不一致立即拒绝，不写新切面。既有姿态的构建提交只有在 `compatible_completed_build_git_commits` 中明确列出时才允许不同于当前恢复实现；旧记录不改写，新记录使用恢复实现的真实提交，最终元数据保留两者及恢复历史。

后端初始化和 GPU/CPU 校准完成后，程序在首个待处理切面前更新 `running` 检查点，并保留 `recovery_history`。完成后最终元数据写 `complete`；普通异常结束时写 `interrupted`。

远程正式任务使用 `setsid` 启动独立 `screen` 会话。运行日志、退出码、PID、screen 会话名和资源采样均使用新的恢复文件名，保留原退出码 129 和原日志作为审计证据。

### 4. 验证

自动测试必须先复现并证明当前缺陷：在第一个渲染调用发生时，`run_metadata.json` 尚不存在。修复后的测试至少覆盖：

- 首个切面前已经存在 `running` 元数据；
- 中断元数据重建拒绝已有元数据、错误预期计数和姿态不一致；
- 合法重建包含协议摘要、精确状态计数和恢复历史；
- 使用重建元数据能够跳过已有样本并完成剩余样本；
- 完成元数据状态为 `complete`，异常中断状态为 `interrupted`；
- 原有完整输出和旧元数据兼容测试继续通过。

服务器恢复前执行只读清单一致性检查和一次脱离 SSH 的 `screen` 存活探针。恢复后持续记录 cgroup 内存、OOM、GPU、磁盘和清单行数；最终必须验证退出码为 0、四类状态之和为 208,250、清单 ID 唯一、所有状态文件计数匹配，并核对最终元数据协议。

## 回退

代码修复使用独立提交，可回退到服务器更新前备份和当前 Git commit。服务器已有 88,280 条结果、原退出文件、原日志和资源 CSV 均不删除、不改名、不覆盖。若任一恢复校验失败，停止续跑并保留现场，不绕过门禁。
